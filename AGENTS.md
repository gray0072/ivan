# AGENTS.md

Instructions for AI coding agents working in this repository.

## What this repo is

A gallery of small, self-contained browser games and experiments, deployed as a static site to GitHub Pages. There is no build tool, no package manager, and no framework — every project is a folder with an `index.html`, its own CSS/JS files, an icon, a screenshot and three READMEs (English, Russian, Swedish). See the root `SPEC.md` for repo-wide conventions and each project's own `<name>/SPEC.md` for that game.

## Ground rules

- **Every game has its own spec, and the spec comes first.** Each project folder contains a `SPEC.md` describing that game (idea, screens, rules, controls incl. touch, difficulty levels, cheats, files) — it is the source of truth for the game. Game-specific details never go into the root `SPEC.md`, which only lists the projects with a one-line summary and a link. When creating a new game, write its `SPEC.md` first and agree on it with the user, then implement the game. When changing a game, update its `SPEC.md` in the same change.
- **English is the primary language.** All in-game text and code comments are in English; `README.md` is English, `README_RU.md` and `README_SV.md` are its translations for players. A game may also be playable in Russian and Swedish (`world-aviation`, `lift-logic`): every text goes through `tr('English text')` and the tables `data/lang-ru.js` / `data/lang-sv.js`. Local-language text is allowed for authenticity next to the English. One language switcher everywhere (**EN · RU · SV**). → [docs/languages.md](docs/languages.md)
- **Translations are maintained, never left behind.** In a translated game every change that adds or rewords a text the player sees updates every language table in the same change, and a change described in `README.md` is described in the other two READMEs; run `node tools/i18n-check.js <folder>` before committing. → [docs/languages.md](docs/languages.md)
- **No build step.** Don't introduce a bundler, framework, or `package.json` unless the user explicitly asks for one for a specific new project. Everything must keep working by opening `index.html` directly or serving the folder as static files.
- **Self-contained projects.** Each project folder should not depend on files outside itself (aside from the shared conventions below). It must work if copied out of the repo on its own.
- **Relative links only.** Every link (gallery card → project, project → screenshot, README image, etc.) must use a relative path, since the site is served from a subpath (`https://gray0072.github.io/ivan/`), not the domain root.
- **Mobile adaptation is required.** Every project works on a phone and a tablet: a responsive, devicePixelRatio-aware layout, fullscreen from the Start button on touch devices, split-screen touch controls (left half a floating joystick, right half the actions) when the game allows it, the mouse cursor hidden in fullscreen, the touch controls described in the READMEs and the in-game instructions. → [docs/mobile.md](docs/mobile.md)
- **Every app is an installable PWA that works offline, with an icon.** Each project has `icon.svg`, `icon-maskable.svg`, PNGs rendered by `tools/pwa-icons.sh`, a `manifest.webmanifest` (`id` = `/ivan/<folder>/`), `update.js` (a new deploy reloads only at an idle moment) and a `sw.js` **generated** by `node tools/sw-build.js` — run it after any change to an app's files, before committing. → [docs/pwa.md](docs/pwa.md)
- **Storage is shared with every app on the origin.** All projects here — and other repos (`/swedish/`, `/tanks/`) — live on one origin, `gray0072.github.io`; folders do not separate `localStorage`, `sessionStorage`, IndexedDB or Cache Storage (the offline caches are named after the app's path, `/ivan/<folder>/offline.<version>`). Every key, database and cache name starts with the project's own prefix (`fishFrenzy.gfx`, `funTraining.v1`, `worldaviation.career.v1`), or with the page's path in code shared between projects (`update.js`). Never call `localStorage.clear()` or delete every cache or database: remove only names with your own prefix.
- **A cloud save is optional and follows [docs/cloud-save.md](docs/cloud-save.md).** One Supabase project is shared with the `swedish` and `tanks` apps: tables, policies and session keys carry the project's prefix. The game plays fully without the cloud and nothing waits for it; every upload is preceded by a read and a merge; what a newer version added is never dropped; a failed load says so on the start screen with **Try again** / **Play with the progress on this device**.
- **Three difficulty levels.** Every game offers exactly three difficulty levels — **Easy**, **Medium**, **Hard** — selectable on the start screen **and** in every restart / game-over / "Play Again" dialog (pre-selected to the current level, so restarting on the same level is one click/keypress). The choice is remembered in `localStorage` between visits. Describe what each level changes in the project's READMEs.
- **Sound can be switched off.** Every game that makes any sound (effects, music, engine noise, spoken callouts) has a **Sound** On / Off switch on its start screen and in its pause dialog (where it has one; a game without a pause adds it to its game-over screen or keeps a 🔊 / 🔇 button in its HUD). The choice is remembered in `localStorage` under the project's prefix (`<prefix>.sound` = `on` / `off`, or the game's own settings object, like `world-aviation`'s `settings.sound`), on by default, and applies at once: every sound goes through one master gain set to 0 (never a flag checked in each sound only), the speech in progress is cancelled and no new one starts. It is read before the first sound, so a game switched off stays silent from its first frame. Speech that is itself the task (`fun-training`'s Reading voice, started by the task or a 🔊 Listen button) may stay on; say so in the spec. Describe the switch in the project's `SPEC.md` and READMEs.
- **Debug cheats.** Every game has simple, easy-to-understand cheats for testing, e.g. digit keys jumping straight to a level / stage / size (`fish-frenzy`: 1–5 = each stage, 6–9 = bigger, 0 = max size). Each cheat shows a short on-screen banner saying what it did. Once any cheat is used in a run, that run is marked as cheated and never updates best times / high scores / records in `localStorage`. Cheats are keyboard-only, aren't mentioned in the in-game instructions and must not trigger by accident during normal play.
- **Arrows and icons are drawn, never shown from a font.** Type the character in a text as usual: the Icons engine turns it into an SVG. After adding one, a new game or a new screen run `node tools/icons-build.js <folder>` and bump what it says; CSS `content`, a canvas and textures are done by hand. → [docs/icons.md](docs/icons.md)
- **Screenshots are in English.** Every `screenshot.png` (and any other preview image) must show the English UI — it's used by all three READMEs, including the Russian and Swedish ones.
- **A game that grows over a long play shows its stages.** When a game changes a lot from its start to its end (eras, chapters, buildings, stages, levels), one screenshot is not enough: take screenshots of its different stages and join them into `<folder>/docs/showcase.gif`, shown at the top of its READMEs; `screenshot.png` stays for the gallery card. The slides are kept as code in `<folder>/tools/showcase-slides.js`, so `node --experimental-websocket tools/showcase.js <folder>` remakes the whole GIF in one go (`arlanda-rising`, `lift-logic`, `fish-frenzy`, `fun-training` are the examples). Remake it when a new stage is added. → [docs/testing.md](docs/testing.md)
- **Start/restart buttons must work everywhere.** Any overlay button (e.g. "Start", "Play Again") must stay tappable on Android/iOS (plain `<button>` elements already are — don't intercept touch events on top of them) and must also be triggerable by **Space** or **Enter** on desktop, via a global `keydown` listener that clicks whichever button is currently visible in the overlay.
- **JS and CSS live in separate files — always.** Never inline `<script>`/`<style>` blocks or `style=`/`onclick=` attributes in a project's `index.html` — put CSS in a `styles.css` and JS in one or more `.js` files (split JS into multiple files by concern/module when it grows large enough to benefit from it; `index.html` just references them). This still satisfies "no build step" and "self-contained" — the extra files live in the same project folder and are plain `<link>`/`<script src>` references, no bundler involved.
- **Game constants live in their own file.** Every gameplay tuning value — sizes, speeds, counts, timings, probabilities, hit shapes, difficulty tables, stage lists — goes into `constants.js` in the project folder, as top-level `const`s with a short comment on units or meaning. It is loaded via `<script src>` before the files that use it; game logic files must not declare their own gameplay constants (purely visual constants of an art/render module, like colour palettes or decoration cell sizes, may stay in that module). Runtime state (arrays of entities, the player object, scores) stays in the logic files.
- **Code is organised into folders by meaning** (`lib/`, `core/`, `data/`, `art/`, `sim/`, `render/`, `ui/`; `world-aviation/` is the reference): data separate from code, logic that doesn't draw, play sounds or show messages but emits game events, shared state in one place, a thin main loop, a header comment on every file, plain scripts (not ES modules) loaded in dependency order. → [docs/code-layout.md](docs/code-layout.md)
- **Version query strings on asset links.** Every `<link>`/`<script src>` referencing a local CSS/JS file must include a `?v=N` query string (e.g. `styles.css?v=2`), and that version must be bumped whenever the referenced file changes, so players don't need to clear their browser cache to see updates.

## Projects

Every project lives in its own folder at the repo root, named in kebab-case (part of the public URL: never renamed once published), with its `SPEC.md`, `index.html`, `styles.css`, `constants.js`, the main loop, its code folders, three READMEs, the icons, the manifest, `sw.js` and a screenshot. **Creating a project: read [docs/new-project.md](docs/new-project.md)** — the full layout and the steps (the spec agreed first, the gallery card, the root READMEs and `SPEC.md`). **A game's card** (the gallery and the root READMEs) carries its English name in every language, a description of at most 50 words, one to four tags from the list in `assets/gallery-lang.js` and its release date — the date of the game's first commit, under its old folder name too (`<time class="released" datetime="YYYY-MM-DD">`). **The games go from newest to oldest**: a new game's card goes first. `node tools/readme-games.js` writes the READMEs' games table from the gallery and checks these limits → [docs/new-project.md](docs/new-project.md#the-games-card).

## Testing the games

No Playwright or Puppeteer: a page is driven in headless Chrome with `tools/cdp.js`, long gameplay tests run in Node. Keep browser runs short and never run several at once. **Read [docs/testing.md](docs/testing.md) before testing.**

**Expect a lot of debugging, and make it cheap.** The bigger games (`arlanda-rising`, `world-aviation`) are debugged again and again — the same questions about the map, the sim and the balance come back. A check you write to answer one is not thrown away: it goes into the game's `tools/` with a header (what it checks, how to run it), a picture you need to see the game's world goes into its `docs/` as a generated file (`arlanda-rising/docs/layout.svg`, the plan written by `tools/layout-check.js`), and a recipe that puts the game into a state goes into its `SPEC.md` → [docs/testing.md](docs/testing.md#tools-and-docs-for-debugging).

## Pitfalls

- **Line endings are LF.** `.gitattributes` (`* text=auto eol=lf`) stores and checks out every text file with LF on every OS, so an editor or a script that writes CRLF does not turn a one-line change into a whole-file diff. Write LF; never commit CRLF.
- **Edit with the editing tools, not `sed -i` or `python -c` one-liners.** Shell quoting mangles escapes: a `'\00d7'` meant for CSS once reached `styles.css` as a NUL byte (git then calls the file binary and the cross never shows). For a scripted change put the script in a file and run it.
- **Bump `?v=N`** in `index.html` for every CSS/JS file a change touches (see Version query strings) — forgetting it leaves players on the old file.
- **Run `node tools/sw-build.js`** after any change to an app's files (after the `?v=N` bumps, `icons-build.js` and `pwa-icons.sh`): a stale `sw.js` keeps the offline copy on the old file list.
- **A cloud save:** go through the "Typical mistakes" of `docs/cloud-save.md` — above all an upload that is not preceded by a read and a merge.
- **A translated game:** run `node tools/i18n-check.js <folder>` before committing; it does not see texts passed to `tr()` through a variable (titles from `data/` tables, rank names), and it does not list keys no longer used — drop those by hand.
