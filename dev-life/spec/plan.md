# Dev Life — the work plan

Part of [SPEC.md](../SPEC.md). How the game is built over the next sessions: what each session does, which work runs **in parallel** and how it is kept **safe** — no two tracks writing the same file, nothing built on a guess that has to be redone. Update this file at the end of every session (what was done, what moved).

## How a session works

- **The main session is the integrator.** It writes the contracts, starts the tracks, merges them, runs the checks, bumps `?v=N`, runs `tools/sw-build.js`, commits, and shows the user the result.
- **A track is an agent in its own git worktree** (`isolation: "worktree"`, a branch `dev-life/<session>-<track>`), with a written brief: the goal, the files it owns, the contracts it builds on, the checks it must pass, what it must not touch. A track commits only its own files and ends with a short report (what was built, what was not, any contract it needed changed).
- **At most four tracks at a time** (the repo's medium workflow size), usually: one **sim** track (Node only), one **content** track (data and texts, Node only), one or two **visual** tracks (render, UI).
- **Each session ends with a review point for the user** — something to look at or play — before the next session builds on it.

## Rules that make parallel work safe

1. **Contracts first, frozen for the session.** Everything tracks share is written down before they start, in `spec/contracts.md` and in code (`sim/state.js`, the stubs): the state's shape, the events' names and data, every `data/` file's entry format, the save format, the card and tab API, the art functions' parameters, the term markup, the fixtures. A track that finds a contract wrong **does not change it**: it says so in its report, works around it with a clearly marked `// CONTRACT:` note, and the integrator changes the contract between sessions.
2. **One owner per file.** Every file is listed under exactly one track in the session's table below. Files not listed are read-only for everyone.
3. **Shared files have sections.** The files every track needs — `constants.js`, `styles.css`, `data/lang-ru.js`, `data/lang-sv.js` — are created in session 1 with one marked section per area (`// ── university ──`, `/* ── hud ── */`…) and a few lines between sections. A track writes **only inside its section**, so git merges the branches without conflicts. Common words (*OK*, *Back*, *Cancel*, month names) go into the `common` section, owned by the UI-kit track.
4. **The integrator owns** `index.html` (all scripts are listed once in session 1, stubs included, so tracks never add lines there), `game.js` (the wiring), the `?v=N` bumps, `sw.js`, `SPEC.md` and this plan. Tracks never bump versions or run `sw-build.js`.
5. **Visual tracks work against fixtures.** `tools/fixtures/*.js` hold sample states (the dorm in 2010, a flat in 2016, a family in 2025, a house in 2038), written by hand in session 1 from the contract, generated by the sim from session 3 (`tools/make-fixtures.js`). Render and UI never wait for the sim and never reach into it beyond `sim/state.js`.
6. **One headless Chrome at a time** (`docs/testing.md`): session 1 adds a lock to `tools/cdp.js` so a second run waits for the first instead of starting a second Chrome. Sim and content tracks test in Node only.
7. **Merge order is fixed:** sim → content → render → UI; after each merge the checks run (below). A failing check is fixed by the integrator or sent back to its track with the error before the next merge.
8. **Look before mass production.** Anything there will be many of — drawings, cards, texts — gets one approved sample first (the look frame in session 1, the first event cards in session 2), so a style is never changed after fifty items are made in it.
9. **The open questions are answered before the data is written** ([SPEC.md › Open questions](../SPEC.md#open-questions)): the currency, the parts' names and the university's length shape `data/` — they are settled at the start of session 1 (the spec's defaults if the user has no preference).

### The checks after every merge

`node tools/i18n-check.js dev-life` · `node dev-life/tools/terms-check.js` · `node dev-life/tools/life-bot.js` (the policies so far) · `node dev-life/tools/save-check.js` · the track's own checker · from session 2 one short browser run (`tools/cdp.js`, the session's steps file: boot, Welcome back, a screenshot per new screen, no page errors).

## The sessions

### Session 1 — Foundations and the look

**First, alone (the integrator):** settle the open questions; write `spec/contracts.md`; create the folder's skeleton — `index.html` listing every planned script, stubs with header comments for every file of [SPEC.md › Files](../SPEC.md#files), `constants.js` / `styles.css` / the language tables with their sections, `core/bus.js`, `core/rng.js`, `core/i18n.js`, `core/storage.js`, the Icons engine copied in, `sim/state.js` with the full state shape, the hand-written fixtures; the lock in `tools/cdp.js`; commit. Then two tracks:

| Track | Owns | Builds | Done when |
|---|---|---|---|
| **A · Core sim** (Node) | `sim/clock.js`, `routine.js`, `meters.js`, `body.js`, `money.js`, `skills.js`, `events.js` (the engine, no content), `save.js`, `yearlog.js`; `tools/sim-files.js`, `tools/life-bot.js`, `tools/save-check.js`; the `sim` sections of `constants.js` | The hour step, the routine with fixed and free hours, the meters' table of effects, diminishing returns, food and weight, money lines, skill XP and rust, the seeded event engine, the save (two slots, checksum, version 1), the bot with *Do nothing* and *Balanced* | 4 years run headless and deterministic; a save/reload at random moments gives the same life |
| **B · Look frame** (visual) | `art/palette.js`, `art/hero.js`, `art/rooms.js` (the dorm only), `render/scene.js` (a first version); the `scene` section of `styles.css` | The art direction on one frame: the dorm room in the cut-away, the hero puppet (look parameters, age, weight, 4 poses: sleep, desk, bed-reading, walk), day and night through the window, the lamp and the monitor's glow | Screenshots of the frame at morning, evening and night, phone and desktop |

**Review point:** the user approves the look (the palette, the hero, the room) — the base all later art follows.
